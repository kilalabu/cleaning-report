## 📚 セクション1: ログレベルと使い分け

### Q1. 一般的なログレベルの優先順位として正しいのは？

- A) DEBUG > INFO > WARN > ERROR
- B) INFO > DEBUG > ERROR > WARN
- C) ERROR > WARN > INFO > DEBUG
- D) WARN > ERROR > DEBUG > INFO

<details>
<summary>答えを見る</summary>

**正解: C**

| レベル | 用途 | 本番で出力? |
|---|---|:---:|
| **ERROR** | 処理が失敗、即座の対応が必要 | ✅ |
| **WARN** | 異常だが処理は継続 | ✅ |
| **INFO** | 正常な処理のマイルストーン | ✅ |
| **DEBUG** | 開発時のデバッグ情報 | ❌ |

</details>

---

### Q2. ERROR と WARN の使い分けとして正しいのは？

- A) どちらも同じ意味
- B) ERROR は処理失敗、WARN は処理は成功したが注意すべき状況
- C) WARN はユーザーエラー、ERROR はシステムエラー
- D) ERROR は復旧可能、WARN は復旧不可能

<details>
<summary>答えを見る</summary>

**正解: B**

| レベル | 使うべき場面 |
|---|---|
| **ERROR** | 処理が失敗、リクエストを完了できない |
| **WARN** | リトライで成功、フォールバック使用など |

**アラート設定の目安:**
- ERROR → 即座に通知
- WARN → 閾値を超えたら通知

</details>

---

### Q3. 本番環境でDEBUGログを有効にすべき状況は？

- A) 常に有効
- B) 絶対に有効にしてはいけない
- C) 特定の問題調査時に一時的に有効
- D) 開発環境専用

<details>
<summary>答えを見る</summary>

**正解: C**

DEBUGログのリスク: ログ量爆発、機密情報漏洩

**安全に有効にする方法:**
- 特定リクエストだけDEBUG（ヘッダーで制御）
- 動的にログレベル変更
- サンプリング（1%だけDEBUG）

</details>

## 📚 セクション2: 構造化ログ

### Q4. 構造化ログのメリットは？

- A) ログファイルのサイズが小さくなる
- B) 人間が読みやすくなる
- C) ログ出力のパフォーマンス向上
- D) 機械で解析しやすく、検索・フィルタリングが容易

<details>
<summary>答えを見る</summary>

**正解: D**

```json
{"timestamp":"2026-01-27T10:00:00Z","level":"INFO","reportId":"123","userId":"456"}
```

Cloud Loggingで`reportId="123"`で検索可能。

</details>

### Q5. リクエストIDの目的は？

- A) 分散システムで1つのリクエストに関連するログを追跡
- B) 認証
- C) キャッシュのキー
- D) DBの主キー

<details>
<summary>答えを見る</summary>

**正解: A**

```
[Service A] requestId=abc-123 Received request
[Service B] requestId=abc-123 Processing
```
→ `abc-123`で検索すると関連ログが見つかる

</details>

## 📚 セクション3: メトリクスとモニタリング

### Q7. REDメソッドの3つのメトリクスは？

- A) Request, Event, Data
- B) Read, Execute, Delete
- C) Rate, Errors, Duration
- D) Response, Error, Debug

<details>
<summary>答えを見る</summary>

</details>

### Q8. パーセンタイル（p50, p95, p99）の意味は？

- A) エラー率の割合
- B) 一定割合のリクエストがその時間以内に完了
- C) CPUの使用率
- D) メモリの使用率

<details>
<summary>答えを見る</summary>

**正解: B**

- p50: 50%のリクエストはこれより速い（中央値）
- p99: 99%のリクエストはこれより速い（最悪ケース近似）

**平均ではなくパーセンタイルを使う理由:** 外れ値に引っ張られない

</details>

---

### Q9. ヘルスチェックで返すべき情報は？

- A) シンプルな生存確認または依存サービスの状態
- B) 詳細なシステム情報
- C) ユーザー認証情報
- D) 機密情報を含む内部状態

<details>
<summary>答えを見る</summary>

**正解: A**

| 種類 | 目的 |
|---|---|
| **Liveness** | プロセス生存確認（200 OK） |
| **Readiness** | リクエスト受付可能か（DB接続等） |

</details>

### Q11. インシデント発生時のログ調査で最初にすべきことは？

- A) 全てのログをダウンロード
- B) DEBUGログを有効にして再現待ち
- C) コードを修正
- D) 問題発生時刻とエラーメッセージで絞り込む

<details>
<summary>答えを見る</summary>

</details>

### Q12. ログの保持期間を決める考慮点は？

- A) できるだけ長く
- B) コンプライアンス、コスト、調査ニーズのバランス
- C) 1週間で十分
- D) リアルタイム分析のみ

<details>
<summary>答えを見る</summary>

**正解: B**

| ログ種類 | 保持期間目安 |
|---|---|
| アクセスログ | 30〜90日 |
| エラーログ | 90日〜1年 |
| 監査ログ | 1〜7年 |
| DEBUGログ | 1〜7日 |

</details>
