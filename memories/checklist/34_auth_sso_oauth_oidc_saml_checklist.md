# 認証・認可・SSO・OAuth/OIDC/SAML 理解度チェックリスト

このチェックリストは、[「ログイン周り」がごちゃつく人へ：認証・認可・SSO・OAuth/OIDC/SAMLの地図](https://qiita.com/ryucciarati/items/800beee69019ca84855c) の内容に基づき、認証・認可・SSOおよび関連プロトコルの用語と概念が正しく区別できているかを確認するために作成されました。

## 前提知識と学習のポイント
- **レイヤー思考の重要性**: Auth周りが混乱する原因は「種類の違う言葉が同じレイヤーに置かれがち」だから。
- **4つのレイヤー**:
  1. **体験の名前** (SSO)
  2. **信頼のつなぎ方** (フェデレーション)
  3. **登場人物の役割** (IdP / SP / RP)
  4. **受け渡しのルール** (OAuth / OIDC / SAML)

## 第1部: 認証と認可の区別 (基礎概念)

### Q1. 「認証 (Authentication / AuthN)」の説明として正しいものはどれですか？
- [ ] A. ユーザーが誰であるかを確認するプロセス
- [ ] B. ユーザーがどのリソースにアクセスできるかを決定するプロセス
- [ ] C. ユーザーにアクセス権限を付与するシステム
- [ ] D. ユーザーの行動ログを記録する仕組み

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: A**

**解説:**
- **A**: 正解。認証（Authentication/AuthN）は「あなたは誰？」という問いに答えるプロセスです。ホテルの例で言えば「チェックイン時の本人確認」に相当します。
- **B, C**: これらは「認可」の説明です。認可は「何をしていいか」を決めるものです。
- **D**: これは監査ログやアクセスログの話であり、認証とは異なる概念です。
</details>

### Q2. 「認可 (Authorization / AuthZ)」の説明として正しいものはどれですか？
- [ ] A. ユーザーが本人であることを確認するプロセス
- [ ] B. ユーザーのパスワードを暗号化する仕組み
- [ ] C. ユーザーが何をできるか（権限）を決めるプロセス
- [ ] D. ユーザーアカウントを作成する処理

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: C**

**解説:**
- **C**: 正解。認可（Authorization/AuthZ）は「あなたは何ができる？」という問いに答えるプロセスです。ホテルの例で言えば「部屋キーで入れる範囲が決まる」ことに相当します。
- **A**: これは「認証」の説明です。
- **B, D**: これらはそれぞれセキュリティやアカウント管理の別の側面であり、認可の定義ではありません。
</details>

### Q3. ホテルのたとえで「認証」と「認可」を説明した場合、正しい組み合わせはどれですか？
- [ ] A. 認証 = 部屋のキーカードを発行する / 認可 = フロントで本人確認をする
- [ ] B. 認証 = ホテルを予約する / 認可 = チェックアウトする
- [ ] C. 認証 = 部屋に入る / 認可 = 朝食を食べる
- [ ] D. 認証 = チェックインで本人確認をする / 認可 = 部屋キーで入れる範囲が決まる

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: D**

**解説:**
- **D**: 正解。記事で説明されている通り、本人確認が「認証」、アクセスできる範囲の決定が「認可」です。
- **A**: 逆になっています。
- **B, C**: これらはホテルの行動ですが、認証・認可の概念とは対応していません。
</details>

### Q4. HTTPステータスコード「401 Unauthorized」と「403 Forbidden」の違いについて、正しい説明はどれですか？
- [ ] A. 401は認可の失敗、403は認証の失敗を意味する
- [ ] B. 401は認証が必要または失敗、403は認証は成功したが権限がないことを意味する
- [ ] C. 401はサーバーエラー、403はクライアントエラーを意味する
- [ ] D. 401と403は同じ意味で、どちらを使っても問題ない

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: B**

**解説:**
- **B**: 正解。
  - **401 (Unauthorized)**: 「あなた誰？」（認証が必要/失敗）
  - **403 (Forbidden)**: 「あなたは分かったけど、それはダメ」（認可で拒否）
- 「ログインできるのに403が出る」のは、認証は成功していて権限が足りないだけというケースが非常に多いです。
- **A**: 逆になっています。
</details>

## 第2部: SSO と フェデレーション
### Q5. 「SSO (Single Sign-On)」の説明として最も適切なものはどれですか？
- [ ] A. 1回のログインで複数のサービスを使える「ユーザー体験」の名前
- [ ] B. 認証結果を別システムに渡すための技術規格
- [ ] C. IdP と SP を接続する仕組みの総称
- [ ] D. SAML の別名

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: A**

**解説:**
- **A**: 正解。SSOは「ユーザー目線」の体験名です。「朝イチでポータルにログインしたら、以降は勤怠もメールも社内Wikiも追加ログインなしで使える」という「便利だな」という感覚がSSOです。
- **B**: これはプロトコル（SAML/OIDCなど）の説明に近いです。
- **C**: これはフェデレーションの説明に近いです。
- **D**: 間違いです。「SSO = SAML」と言い切るとズレます。SSOは体験名、SAMLは規格です。
</details>

### Q6. 「フェデレーション」の説明として最も適切なものはどれですか？
- [ ] A. ユーザーが1回ログインすれば他のサービスも使える便利な機能
- [ ] B. 認証を行うサーバーのこと
- [ ] C. 別システムの認証結果を「信頼して受け取る」仕組み
- [ ] D. OAuth 2.0 の別名

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: C**

**解説:**
- **C**: 正解。フェデレーションは「システム目線」の仕組みです。「Aが認証した結果を、Bが受け入れる」という信頼の仕組みがフェデレーションです。
- **A**: これはSSOの説明です。SSOという体験を支える土台としてフェデレーションがよく登場します。
- **B**: これはIdPの説明に近いです。フェデレーションは「誰か」ではなく「仕組み」です。
- **D**: 間違いです。
</details>

### Q7. 「SSO」と「フェデレーション」の関係について、正しい説明はどれですか？
- [ ] A. SSO と フェデレーション は同じ意味である
- [ ] B. フェデレーション は SSO を実現するための仕組みの一つである
- [ ] C. SSO は フェデレーション を実現するための規格である
- [ ] D. SSO と フェデレーション は完全に独立した概念で関係がない

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: B**

**解説:**
- **B**: 正解。
  - **SSO**: ユーザー体験（1回ログインで複数サービスを使える）
  - **フェデレーション**: その体験を支える信頼の仕組み（Aの認証結果をBが受け入れる）
- SSOという「体験」を実現するために、フェデレーションという「仕組み」を使うことが多いという関係です。
</details>

### Q8. 企業がフェデレーションを導入することで解決できる課題として、**当てはまらない**ものはどれですか？
- [ ] A. 各SaaSごとにユーザーアカウントを個別管理する運用負荷
- [ ] B. 退職者のアカウント削除漏れによるセキュリティリスク
- [ ] C. ユーザーが複数のパスワードを管理する負担
- [ ] D. アプリケーションのレスポンス速度の向上

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: D**

**解説:**
- **D**: 正解。フェデレーションは「認証を一元化する」仕組みであり、アプリケーションの処理速度向上とは直接関係ありません。むしろ認証時に外部IdPへのリダイレクトが発生するため、わずかなオーバーヘッドが生じる場合もあります。
- **A**: フェデレーションにより、認証はIdP側で一括管理され、各サービスでの個別ユーザー管理が不要になります。
- **B**: IdP側でアカウントを無効化すれば、連携しているすべてのサービスへのアクセスが停止されるため、削除漏れのリスクが減ります。
- **C**: ユーザーはIdPへの1つの認証情報で複数サービスにアクセスできるため、パスワード管理の負担が軽減されます（これがSSOの体験）。
</details>

## 第3部: IdP と SP/RP

### Q9. 「IdP (Identity Provider)」の役割として正しいものはどれですか？
- [ ] A. サービスを提供し、ユーザーにログインを要求する側
- [ ] B. 認証結果を受け取って検証する側
- [ ] C. OAuth 2.0 の Access Token を発行するAPI
- [ ] D. 本人確認をして「認証済み」を発行する側

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: D**

**解説:**
- **D**: 正解。IdP（Identity Provider）は「認証する側」「ログイン元」であり、本人確認して「認証済み」を発行する役割を担います。
- **A, B**: これらは SP/RP の役割です。
- **C**: OAuth 2.0 の Authorization Server とは関連しますが、IdP の定義としては不正確です。
</details>

### Q10. 「SP (Service Provider)」と「RP (Relying Party)」の役割として正しいものはどれですか？
- [ ] A. 本人確認をして認証結果を発行する側
- [ ] B. 認証結果を受け取り、検証してサービスを提供する側
- [ ] C. ユーザーのパスワードを保管する側
- [ ] D. SAML アサーションを作成する側

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: B**

**解説:**
- **B**: 正解。SP（Service Provider）/ RP（Relying Party）は「サービス提供側」であり、IdPの認証結果を受け取り、検証してログインを成立させ、サービスを提供する役割を担います。
- **A, D**: これらは IdP の役割です。
- **C**: パスワード保管は IdP の責務であり、SP/RP はパスワードを知る必要がありません（これがフェデレーションの利点）。
</details>

### Q11. フェデレーションにおける IdP と SP/RP の関係について、正しい説明はどれですか？
- [ ] A. フェデレーションは IdP のことである
- [ ] B. SP/RP が IdP に認証結果を送信する
- [ ] C. IdP と SP/RP はフェデレーションという仕組みの中の「登場人物（役割）」である
- [ ] D. IdP と SP/RP は常に同じサーバー上に存在する

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: C**

**解説:**
- **C**: 正解。
  - **フェデレーション**: Aの認証結果をBが受け入れる「仕組み全体」
  - **IdP**: その中の「認証して結果を出す役割」
  - **SP/RP**: その結果を受け取って利用させる役割
- **A**: フェデレーションは仕組み全体であり、IdP はその登場人物の一つです。
- **B**: 逆です。IdP が SP/RP に認証結果を送信します。
</details>

### Q12. IdP が認証結果として発行するものについて、正しい説明はどれですか？
- [ ] A. OIDC では ID Token（JWT形式）、SAML では Assertion（XML形式）を発行する
- [ ] B. どちらのプロトコルでも Access Token のみを発行する
- [ ] C. IdP は認証結果を発行せず、SP/RP が自ら生成する
- [ ] D. OIDC では Assertion（XML形式）、SAML では ID Token（JWT形式）を発行する

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: A**

**解説:**
IdPが発行する「認証結果を証明するもの」は、使用するプロトコルによって形式と呼び方が異なります。

| プロトコル | IdPが発行するもの | 形式 |
|------------|------------------|------|
| **OIDC** | ID Token | JWT (JSON Web Token) |
| **SAML** | Assertion（アサーション） | XML |

- **A**: 正解。プロトコルごとに発行物の名前と形式が異なります。
- **B**: Access Token は認可（権限）のためのトークンであり、「誰か」を証明する認証結果とは別です。
- **C**: 逆です。IdP が認証結果を発行し、SP/RP がそれを受け取って検証します。
- **D**: 逆になっています。
</details>

### Q13. SP/RP が IdP から受け取った認証結果を「検証する」とは、具体的に何を確認することですか？
- [ ] A. 認証結果（ID Token や SAML Assertion）がIdPの秘密鍵で署名されており、改ざんされていないこと
- [ ] B. IdPでの認証時に入力されたパスワードが正しかったこと
- [ ] C. 認証結果の有効期限が切れていないこと
- [ ] D. 認証結果が自分（このSP/RP）宛に発行されたものであること

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: A, C, D**

**解説:**
SP/RPが行う「検証」は、**IdPから受け取った認証結果（ID Token や SAML Assertion）そのものの正当性を確認すること** です。IdPが行った本人確認（パスワード照合など）を再度やり直すのではありません。

- **A**: 正解。署名検証により、本当にそのIdPが発行したか、途中で改ざんされていないかを確認します。
- **B**: 間違い。パスワードの正誤はIdP側で完了しています。SP/RPはパスワードを知る必要がありません（これがフェデレーションの利点）。
- **C**: 正解。期限切れの認証結果は古いものの再利用（リプレイ攻撃）を防ぐため拒否します。
- **D**: 正解。他のサービス宛に発行された認証結果を流用されるのを防ぎます（audience検証）。

**ホテルのたとえ:**
- IdP = パスポートを発行した「政府」（本人確認を実施）
- SP/RP = パスポートを見せられた「ホテルのフロント」
  - ✓ 本物の政府が発行したパスポートか？（署名検証）
  - ✓ 有効期限は切れていないか？
  - × パスワード（本人確認方法）を自分で調査するわけではない
</details>

### Q14. 「RP (Relying Party)」という用語がよく使われるコンテキストはどれですか？
- [ ] A. SAML プロトコル
- [ ] B. OAuth 2.0 / OIDC プロトコル
- [ ] C. LDAP によるディレクトリサービス
- [ ] D. Kerberos 認証

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: B**

**解説:**
- **B**: 正解。OIDC / OAuth 2.0 の文脈では「RP (Relying Party)」という用語が使われます。
- **A**: SAML では「SP (Service Provider)」という用語が使われます。
- SP と RP は役割としては同じ（認証結果を受け取ってサービスを提供する側）ですが、使われるプロトコルの文化によって呼び方が異なります。
</details>

## 第4部: OAuth 2.0

### Q15. OAuth 2.0 の主な目的として正しいものはどれですか？
- [ ] A. ユーザーが誰であるかを確認する（認証）
- [ ] B. ユーザーのパスワードを暗号化して保存する
- [ ] C. パスワードを渡さずに権限だけを渡す（認可/権限委譲）
- [ ] D. シングルサインオン体験を提供する

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: C**

**解説:**
- **C**: 正解。OAuth 2.0 の主役は「ログイン」ではなく「権限の委譲」です。例えば「写真プリントアプリがあなたの写真を読み取りたいが、アプリにGoogle ID/PWを渡すのは嫌」という場合に、「写真の読み取りだけOK」と範囲を絞って許可できる仕組みです。
- **A**: これは認証の話であり、OAuth 2.0 の中心的目的ではありません。
- **D**: SSOは体験の名前であり、OAuth 2.0 の目的とは異なります。
</details>

### Q16. 「OAuthで認証してます」という表現について、正しい評価はどれですか？
- [ ] A. 技術的に正確で問題ない表現である
- [ ] B. OAuth の中心は「認可」なので、文脈によってはズレた表現になる
- [ ] C. OAuth は認証専用のプロトコルなので、完全に正しい
- [ ] D. OAuth と OIDC は同じなので、問題ない表現である

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: B**

**解説:**
- **B**: 正解。OAuth 2.0 の中心はあくまで「許可（認可）」です。「OAuthで認証してます」と言うと、文脈によっては技術的にズレた表現になります。
- 正確には、OAuth 2.0 は「ID/PWを渡さない代わりに、この範囲だけOKな通行証（Access Token）を渡す」仕組みです。
- 認証が必要な場合は、OAuth 2.0 の上に認証を足した OIDC を使うのが正確です。
</details>

### Q17. OAuth 2.0 で発行される「Access Token」の役割として正しいものはどれですか？
- [ ] A. ユーザーが誰であるかを証明する身分証
- [ ] B. ユーザーのパスワードの代わり
- [ ] C. 次回ログイン時に使用する永続的なトークン
- [ ] D. 特定の範囲の操作を許可する「通行証」

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: D**

**解説:**
- **D**: 正解。Access Token は「この範囲だけOK」という通行証（権限）であり、特定のAPIにアクセスするための許可証として機能します。
- **A**: これは ID Token（OIDC）の役割です。Access Token は「誰か」は表現せず、「何ができるか」を表現します。
- **B**: パスワードの代わりというより、パスワードを渡さずに済むようにするための仕組みです。
- **C**: Access Token は通常短命であり、永続的なものではありません。
</details>

## 第5部: OIDC

### Q18. OIDC (OpenID Connect) の説明として正しいものはどれですか？
- [ ] A. OAuth 2.0 とは全く別の独立したプロトコル
- [ ] B. OAuth 2.0 の仕組みを使いつつ、「あなたは誰か」という認証の結果を扱えるようにしたもの
- [ ] C. OAuth 2.0 の古いバージョン
- [ ] D. SAML の後継プロトコル

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: B**

**解説:**
- **B**: 正解。OAuth 2.0 だけでは「このトークンで写真APIを読める」は表現できても、「この人は誰か」は扱えません。OIDC は OAuth 2.0 の仕組みを使いつつ、認証の結果（あなたは誰か）を扱えるようにしたものです。
- **A**: OIDC は OAuth 2.0 の「上に」構築された拡張であり、独立したプロトコルではありません。
- **C**: 逆です。OIDC は OAuth 2.0 を拡張したより新しい規格です。
</details>

### Q19. OIDC で追加される「ID Token」の役割として正しいものはどれですか？
- [ ] A. API にアクセスするための通行証
- [ ] B. Access Token を更新するための鍵
- [ ] C. セッション管理のためのCookie
- [ ] D. 「あなたは誰か」を示す身分証（ユーザー情報）

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: D**

**解説:**
- **D**: 正解。ID Token は「あなたは誰か」の身分証であり、ユーザーIDやメールアドレスなどのユーザー情報を含みます。
- **A**: これは Access Token の役割です。
- **B**: これは Refresh Token の役割です。
- トークンは用途で区別すると混乱しにくくなります：
  - **Access Token**: API行くための通行証（権限）
  - **ID Token**: 「あなたは誰か」の身分証（ユーザー情報）
  - **Refresh Token**: Access Token を更新する鍵
</details>

### Q20. OIDC が「認証 + 認可」に見える理由として正しいものはどれですか？
- [ ] A. OIDC は認証だけを扱うプロトコルだから
- [ ] B. 現場では Access Token も一緒に扱うことが多いから
- [ ] C. ID Token と Access Token は同じものだから
- [ ] D. OIDC は OAuth 2.0 を置き換えたから

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: B**

**解説:**
- **B**: 正解。OIDC が「認証 + 認可」に見えるのは、現場では Access Token（認可）と ID Token（認証）を一緒に扱うことが多いからです。
- ただし、OIDC が「追加している本体」は「認証（ID Token）」の側だと押さえておくと混線しにくくなります。
- OIDC = OAuth 2.0（認可）+ ID Token による認証
</details>

### Q21. アプリ開発者が「Googleログイン」を実装してユーザー情報を取得したい場合、どのプロトコルを使うのが最も適切ですか？
- [ ] A. OAuth 2.0 のみ
- [ ] B. OIDC (OpenID Connect)
- [ ] C. SAML 2.0
- [ ] D. HTTP Basic 認証

<details>
<summary><strong>正解と解説を確認する</strong></summary>

**正解: B**

**解説:**
- **B**: 正解。「この人をユーザーとして登録したい」「ログイン状態を作りたい」「メールアドレスやユーザーIDがほしい」といった要件がある場合、OIDC を使うのが適切です。
- **A**: OAuth 2.0 だけでは「誰か」の情報を標準的に取得できません。
- **C**: SAML でも技術的には実装可能ですが、一般的なWebアプリやモバイルアプリのソーシャルログインには OIDC の方が適しています。SAML は主に企業間のSSO連携（例: 社内システムとSalesforceの連携）で使われます。また、SAML は XML ベースでモバイルアプリでは扱いにくいという実装上の理由もあります。
</details>

### Q25. 「SSO = SAML」という理解について、正しい評価はどれですか？

- [ ] B. SSO と SAML は完全に同じ意味である
- [ ] C. SSO は SAML を含んでいない
