## 📚 セクション1: Dockerの基礎概念とメリット・デメリット

### Q1. Dockerを一言で説明するとしたら、最も適切なのは？

- A) 仮想マシン（VM）を簡単に作成するためのツール
- B) アプリケーションとその実行環境を「コンテナ」という単位でパッケージ化し、どこでも同じように動かせるようにする技術
- C) Linux専用のサーバー管理ツール
- D) クラウドサービスを利用するための必須ソフトウェア

<details>
<summary>答えを見る</summary>

**正解: B**

**解説:**
Dockerは「**コンテナ型仮想化技術**」です。アプリケーションのコード、ライブラリ、設定ファイルなど、動作に必要なすべてを「コンテナ」という箱にまとめます。この箱を開発マシン、テストサーバー、本番サーバーのどこに持っていっても、まったく同じように動作します。

**❌ 不正解の解説:**
- **A**: VMとコンテナは根本的に異なる技術です（Q5で詳しく解説）。
- **C**: Mac、Windowsでも動作します（Docker Desktop経由）。
- **D**: ローカル開発でも使えます。クラウドは必須ではありません。

</details>

### Q2. Dockerを使う最大のメリットは何か？

- A) 「自分のPCでは動いたのに、サーバーでは動かない」という環境差異の問題を解消できる
- B) アプリケーションの実行速度が2倍以上高速化する
- C) プログラミング言語に関係なく、すべてのアプリが自動的に動作する
- D) サーバーの電気代を90%削減できる

<details>
<summary>答えを見る</summary>

**正解: A**

**解説:**
**「It works on my machine（自分の環境では動く）」問題**はエンジニアの永遠の悩みです。Dockerを使えば、開発環境と本番環境で**全く同じコンテナイメージ**を使うため、「環境差異」という概念自体がなくなります。

**具体例:**
- Python 3.9で開発したコードが、本番サーバーはPython 3.8だったため動かない → Dockerなら同じPythonバージョンが保証される
- 開発PCにはライブラリXが入っていたが、本番サーバーにはなかった → Dockerならライブラリも含めてパッケージ化

**❌ 不正解の解説:**
- **A**: コンテナはVMより軽量ですが、ネイティブ実行と比べて速くなるわけではありません。
- **C**: Dockerfileを適切に書く必要があります。自動では動きません。

</details>

### Q3. Dockerを使うことのデメリット・注意点として正しいものは？

- A) 学習コストがゼロで、すぐに使いこなせる
- B) Windows/Macでは動作しない
- C) コンテナ技術やLinuxコマンドなど、一定の学習コストがあり、チーム全体での理解が必要になる
- D) 一度Dockerfileを書けば、OSアップデートなどのメンテナンスは一切不要になる

<details>
<summary>答えを見る</summary>

**正解: C**

**解説:**
Dockerは非常に便利ですが、以下のデメリット・注意点があります：

1. **学習コスト**: Dockerfile、docker-compose、ネットワーク、ボリュームなど覚えることが多い
2. **チーム全体の理解**: 一部のメンバーだけが理解していても、全員が使えないと効果が薄れる
3. **デバッグの複雑さ**: コンテナ内部の調査にはDockerコマンドの知識が必要
4. **パフォーマンスオーバーヘッド**: 特にMac/WindowsではDocker Desktop経由のため、ファイルI/Oが遅くなることがある

**❌ 不正解の解説:**
- **A**: 基礎を習得するのに数日〜数週間は必要です。
- **B**: Docker Desktopを使えば問題なく動作します。
- **D**: ベースイメージのセキュリティアップデートなど、定期的なメンテナンスは必要です。

</details>

### Q4. 以下のうち、Dockerを導入すべき**ではない**ケースとして最も適切なのは？

- A) 1行のシェルスクリプトを1回だけ実行したい（使い捨て）
- B) 本番サーバーへのデプロイを自動化し、確実に動作させたい
- C) 開発チームが5人以上いて、各自のPCで同じ環境を再現したい
- D) マイクロサービスで複数のサービスをそれぞれ独立してデプロイしたい

<details>
<summary>答えを見る</summary>

**正解: A**

**解説:**
Dockerは「**繰り返し使う環境**」や「**チームで共有する環境**」に最大の効果を発揮します。1回きりの使い捨てスクリプト実行には、Dockerfile作成などのオーバーヘッドに見合いません。

**Dockerが特に有効なユースケース:**
- ✅ チーム開発での環境統一
- ✅ CI/CDパイプラインでの自動テスト・デプロイ
- ✅ マイクロサービスアーキテクチャ
- ✅ 複数バージョンのランタイム（Node 16/18/20など）を切り替えたい
- ✅ 本番と同じ環境でローカル開発したい

**Dockerが不要または過剰なケース:**
- ❌ 1回きりの単純なスクリプト実行
- ❌ 極めて高いI/O性能が求められるアプリ（データベースサーバーなど）

</details>

## 📚 セクション2: コンテナと仮想マシンの違い

### Q5. Dockerコンテナと仮想マシン (VM) の構造的な違いに関する説明で、正しいものは？

- A) VMはホストOSの上に「ハイパーバイザ」を介してゲストOSを動作させるが、DockerコンテナはホストOSの「カーネル」を共有し、プロセスとして動作する
- B) DockerコンテナはVMの一種であり、軽量化されたゲストOS（Linux Kernel）を個別に持っているため、起動が少し遅い
- C) VMはハードウェアをエミュレーションするが、DockerはCPUやメモリを直接占有するため、ホストOSからはプロセスとして見えない
- D) Dockerコンテナはアプリケーションコードしか持たず、OSの機能（ファイルシステムやネットワーク）は持っていない

<details>
<summary>答えを見る</summary>

**正解: A**

**解説:**

```
【仮想マシン (VM)】              【Dockerコンテナ】
┌────────────────┐            ┌────────────────┐
│   アプリ A     │            │   アプリ A     │
├────────────────┤            ├────────────────┤
│  ゲストOS A    │            │  コンテナ A    │
│  (Ubuntu等)   │            │  (プロセス)    │
├────────────────┤            ├────────────────┤
│ ハイパーバイザ │            │ Docker Engine  │
├────────────────┤            ├────────────────┤
│   ホストOS     │            │   ホストOS     │
└────────────────┘            └────────────────┘
```

- **VM**: 完全に独立したOS（ゲストOS）を動かすため、GB単位のメモリを消費し、起動に分単位かかる。
- **Docker**: ホストOSのカーネルを共有するため、MB単位のオーバーヘッドで、秒単位で起動。

**💡 用語の補足:**
- **ハイパーバイザ**: 物理マシン上で複数のOSを動かすための土台となるソフトウェア（VirtualBox, VMware, Hyper-Vなど）。「ハードウェアをまるごとシミュレート」してその上に別のOSを乗せるため、重くなります。
- **カーネル**: OSの核心部分。CPUやメモリの管理、アプリからハードウェアへの命令転送などを行います。Dockerは「家（カーネル）を共有して、部屋（コンテナ）だけ分ける」イメージです。

**❌ 不正解の解説:**
- **B**: DockerはゲストOSを持ちません。これがVMとの最大の違いです。
- **C**: DockerプロセスはホストOSから普通に見えます（`ps aux` で確認可能）。

</details>

### Q6. なぜDockerコンテナはVMより軽量で起動が速いのか？

- A) Dockerが高度な圧縮技術を使っているから
- B) コンテナはメモリ上だけで動作し、ディスクを使わないから
- C) DockerはIntel製CPUでしか動作しないよう最適化されているから
- D) ホストOSのカーネル（Linux）を共有し、個別のOSを起動する必要がないから

<details>
<summary>答えを見る</summary>

**正解: D**

**解説:**
VMが重い理由は「**完全なOSを毎回起動する**」からです。
- Ubuntuをインストール → 数GB
- 起動プロセス → 数十秒〜数分

Dockerコンテナは「**ホストのLinuxカーネルを借りる**」ので：
- 起動するのはアプリのプロセスだけ
- オーバーヘッドは最小限
- 起動は数秒以内

**例え話:**
- **VM** = 毎回新しい家を建てて住む
- **Docker** = シェアハウス（カーネル）の一室を借りる

</details>

## 📚 セクション3: Dockerの構成要素

### Q7. 「Dockerイメージ」と「Dockerコンテナ」の関係として正しいのは？

- A) イメージとコンテナは同じものを指す別名である
- B) イメージは「設計図（テンプレート）」であり、コンテナは「その設計図から作られた実体（インスタンス）」である
- C) コンテナを圧縮したものがイメージになる
- D) イメージはローカル専用、コンテナはクラウド専用である

<details>
<summary>答えを見る</summary>

**正解: B**

**解説:**
プログラミングの「クラスとインスタンス」の関係と同じです。

```
【クラス → インスタンス】
class User { ... }  → user1 = new User()
                    → user2 = new User()

【Dockerイメージ → コンテナ】
nginx:latest        → nginx_container_1
(イメージ)          → nginx_container_2
                    (複数作成可能)
```

- **イメージ**: 読み取り専用のテンプレート。Dockerfileからビルドして作る。
- **コンテナ**: イメージから起動した実行中のプロセス。停止・削除が可能。

</details>

### Q8. Dockerイメージの「レイヤー構造」について正しい説明は？

- A) 上位のレイヤーでファイルを削除すると、下位のレイヤーからも物理的にファイルが削除され、イメージサイズが小さくなる
- B) レイヤー構造はコンテナ実行時のメモリ使用量を減らすための仕組みであり、ディスク容量には影響しない
- C) イメージはビルド日時ごとにスナップショットが取られるため、古いレイヤーを削除するにはイメージ全体を作り直す必要がある
- D) イメージは「読み取り専用の層（レイヤー）」の積み重ねでできており、変更された層以降だけを再ビルドすれば良いため、キャッシュが効きやすい

<details>
<summary>答えを見る</summary>

**正解: D**

**解説:**
Dockerイメージは「不変（ReadOnly）なレイヤー」の積み重ねです。Dockerfileの各命令（`FROM`, `RUN`, `COPY`など）が1つのレイヤーを作成します。

**レイヤー構造のメリット（キャッシュ機能）:**
一度ビルドしたレイヤーは、その内容が変わらない限り再利用されます。
```
┌─────────────────────────────┐
│ Layer 4: COPY app.jar      │ ← ソース変更時、ここから下を再ビルド
├─────────────────────────────┤
│ Layer 3: RUN gradle build  │ ← 前のレイヤーが同じならキャッシュから即終了
├─────────────────────────────┤
│ Layer 2: RUN apt install   │ ← 同上
├─────────────────────────────┤
│ Layer 1: FROM ubuntu:22.04 │ ← ベースイメージ
└─────────────────────────────┘
```

**❌ 不正解の解説:**
- **A**: **超重要！** Docker初心者が最もハマるポイントです。
    - **イメージ:** 「紙に油性ペンで描いた絵」を想像してください。間違えた箇所を上から白い修正液で塗りつぶしても、下のインク（データ）は消えずに残っていますよね？Dockerも同じで、次のレイヤーで `rm` しても「見えなくする（ホワイトアウト）」だけで、物理的なデータは残り続けます。
    - **悪い例:**
        ```dockerfile
        RUN wget http://example.com/big-file.zip  # ← ここで1GBのレイヤーが確定（保存される）
        RUN rm big-file.zip                       # ← 次のレイヤーで消しても、サイズは1GBのまま！
        ```
    - **どうすればいいの？:** レイヤーが確定する前に消す必要があります。「1つの `RUN` 命令」の中で作って消します。
        ```dockerfile
        # && で繋ぐと1つのレイヤーとみなされる
        RUN wget http://example.com/big-file.zip \
            && unzip big-file.zip \
            && rm big-file.zip  # ← レイヤー確定前に消えるので、イメージサイズは増えない！
        ```
- **B**: むしろ**ディスク容量を節約するための仕組み**です。同じベースイメージ（Ubuntuなど）を使う複数のイメージがある場合、共通のレイヤーは物理的に1つしか保存されません。
- **C**: 「全体を作り直す」必要はありません。Dockerは変更があったレイヤーとそれ以降のレイヤーだけを更新します。これを **「ビルドキャッシュ」** と呼びます。

</details>

### Q9. 「Dockerfile」とは何か？

- A) Dockerコンテナの実行ログを記録するファイル
- B) Dockerイメージを構築するための手順書（レシピ）であり、「どのベースイメージを使い、何をインストールし、どのファイルをコピーするか」を記述するテキストファイル
- C) Docker Hubにログインするための認証情報ファイル
- D) 複数のコンテナを一括管理するための設定ファイル

<details>
<summary>答えを見る</summary>

**正解: B**

**解説:**
Dockerfileは「**イメージの作り方**」を記述したテキストファイルです。

```dockerfile
# Dockerfileの例
FROM node:18-alpine       # ベースイメージを指定
WORKDIR /app              # 作業ディレクトリを設定
COPY package*.json ./     # 依存関係ファイルをコピー
RUN npm install           # 依存関係をインストール
COPY . .                  # ソースコードをコピー
EXPOSE 3000               # ポートを公開
CMD ["npm", "start"]      # 起動コマンド
```

このファイルを `docker build` コマンドで実行すると、Dockerイメージが作成されます。

**❌ 不正解の解説:**
- **D**: それは `docker-compose.yml` です（後述）。

</details>

### Q10. 「Docker Compose」とは何か？DockerfileとDocker Composeの違いは？

- A) Docker Composeは複数のホストサーバーを管理するクラスタリングツール
- B) Docker Composeは「1つのイメージをビルドする手順」を書くもので、Dockerfileの代替
- C) Docker Composeは「複数の関連するコンテナ（Web、DB、Redisなど）の構成をまとめて定義し、一括で起動・停止する」ためのツール。Dockerfileが「1つのイメージの作り方」なら、Docker Composeは「システム全体の構成図」
- D) Docker Composeはv1とv2で全く互換性がなく、現在は非推奨

<details>
<summary>答えを見る</summary>

**正解: C**

**解説:**

| 項目 | Dockerfile | Docker Compose |
|------|-----------|----------------|
| **目的** | 1つのイメージをビルドする | 複数コンテナを一括管理する |
| **ファイル形式** | 独自形式 | YAML形式 |
| **コマンド** | `docker build` | `docker compose up` |
| **例え** | 「料理のレシピ」 | 「コース料理のメニュー表」 |

```yaml
# docker-compose.yml の例
services:
  web:
    build: .             # ← 自分のアプリ。Dockerfileを使ってビルドする！
    ports:
      - "3000:3000"
  db:
    image: postgres:15   # ← 既存のイメージを使う（ビルドしない）
    environment:
      POSTGRES_PASSWORD: secret
  redis:
    image: redis:7       # ← 既存のイメージを使う
```

この1ファイルで、Web・DB・Redisの3つのコンテナを `docker compose up` 一発で起動できます。

**Dockerfileとの関係性:**
Docker Composeは「複数のDockerfileをまとめるもの」という理解は部分的です。
- **build: .**: 指定したディレクトリの `Dockerfile` をビルドして使用します（自作アプリなど）。
- **image: ...**: Docker Hub等の既存イメージをそのまま使用します（DBやRedisなど）。

つまり、Docker Composeは「自作のDockerfile」と「既存のイメージ」を組み合わせて、1つのシステムとして定義・実行するためのツールです。

**作業効率の向上:**
Composeを使用することで、複数のコンテナ管理が劇的に簡略化されます。
- **Composeなし:** Web, DB, Redisなどを個別のターミナルで手動で起動・管理する必要があり、手順が繁雑になります。
- **Composeあり:** `docker compose up` コマンド1つだけで、定義された全サービスを一括で起動・連携させることができます。

</details>

## 📚 セクション4: Dockerの基本操作

### Q11. `docker run -p 8080:80 nginx` におけるポートマッピングの挙動として正しいのは？

- A) コンテナ内のポート8080を、ホストのポート80に転送する
- B) コンテナ間通信のためにポート80を使用する設定
- C) セキュリティのためにポート8080への外部アクセスをブロックする
- D) ホストマシンのポート8080へのアクセスを、コンテナ内のポート80へ転送する

<details>
<summary>答えを見る</summary>

**正解: D**

**解説:**
基本から順番に理解していきましょう！

**1. 言葉の定義**
- **ホストOS:** あなたがいま使っているPC（MacやWindows）。
- **コンテナ:** PCの中に隔離された「小さな別のPC」。
- **ポート:** ネットワークの「ドア番号」。Webサーバは通常80番、PostgreSQLは5432番のドアで待ち構えています。

**2. なぜ設定が必要？（マンションの例え）**
コンテナはデフォルトで外界から遮断された「鍵のかかった部屋」です。
- コンテナ（部屋）の中では、Nginxさんが「80番のドア」の前で来客を待っています。
- しかし、あなた（ブラウザ）はマンションの外（ホストOS）にいて、オートロックに阻まれて中に入れません。

そこで `8080:80` という設定（ポートフォワーディング）をします。
**「マンションの入り口（ホスト）の8080番インターホンを押したら、自動的に部屋（コンテナ）の中の80番に繋いでね！」** という転送設定です。

**3. 図解**
```
あなた（ブラウザ）
   │
   ▼ アクセス (http://localhost:8080)
┌─────────────────────────────────┐
│ ホストOS (Mac/Win)              │
│  [ ポート 8080 ] ← ここで受付！ │
│        │ 転送 (Forward)         │
│        ▼                        │
│ ┌─────────────────────┐         │
│ │ コンテナ (Nginx)    │         │
│ │  [ ポート 80 ]      │ ← ここに届く！
│ └─────────────────────┘         │
└─────────────────────────────────┘
```
この設定がないと、外からいくらノックしてもコンテナには届きません。
`-p 外のドア:中のドア` と覚えましょう！

</details>

### Q12. コンテナを削除 (`docker rm`) した場合、コンテナ内で生成されたファイル（ログやDBデータ）はどうなる？

- A) イメージの一部としてコミットされるため、次回同じイメージから起動した際に復元される
- B) 自動的にホストの `/var/lib/docker/backup` にバックアップされる
- C) コンテナ内の書き込みレイヤー (CoW) にあるデータは、コンテナ削除とともに完全に消滅する
- D) `--volumes` オプションを付けない限り保持され続ける

<details>
<summary>答えを見る</summary>

**正解: C**

**解説:**
コンテナの**書き込みレイヤー（Read-Write Layer）**と、イメージの**読み取り専用レイヤー（Read-Only Layer）**の違いを理解することが重要です。

- **イメージのレイヤー (Q8):** `docker build` で作られる不変の層です。これらは物理的に永続化されており、コンテナを削除してもイメージ自体はホストに残ります。
- **コンテナの書き込みレイヤー (Q12):** `docker run` した瞬間に、イメージの一番上に作成される**一時的な書き込み可能な層**です。

```
【コンテナの構造】
┌─────────────────────┐
│ 書き込みレイヤー    │ ← 🌟ここ！ログやDBデータはここに書かれる
├─────────────────────┤
│ イメージ Layer 3    │
│ イメージ Layer 2    │ ← こっちはReadOnly（不変）
│ イメージ Layer 1    │
└─────────────────────┘
```

**結論:**
コンテナを削除 (`docker rm`) すると、この一番上の **「書き込みレイヤー」のみが丸ごと物理削除されます。**
下の「イメージ層」は削除されませんが、書き込みレイヤーに含まれていた変更差分（DBのレコードやログファイルなど）は、この層と共に消滅します。

**この特性への対策:**
データの永続化には「Volume」を使用します（次の問題で解説）。

**❌ 不正解の解説:**
- **A**: イメージは読み取り専用です。コンテナの書き込みは反映されません。
- **D**: これは**Volume**を使っていた場合の挙動です。

</details>

### Q13. `docker volume` (ボリューム) を使う主な理由は何か？

- A) コンテナを削除してもデータが消えないよう、ホスト側にデータを永続化するため
- B) コンテナの起動速度を上げるため
- C) コンテナのメモリ使用量を節約するため
- D) 複数のDockerホストでデータを自動的に同期するため

<details>
<summary>答えを見る</summary>

**正解: A**

**解説:**
**Docker Volume** は、コンテナのライフサイクルから独立した「**永続的な保存領域**」です。

```
【Volumeなしの場合】
コンテナ削除 → DBデータも消える！💀

【Volumeありの場合】
コンテナ削除 → DBデータはVolumeに残る！✅
新しいコンテナ起動 → 同じVolumeをマウント → データ復活！
```

```yaml
# docker-compose.yml での例
services:
  db:
    image: postgres:15
    volumes:
      - db-data:/var/lib/postgresql/data  # ← ここで永続化！

volumes:
  db-data:  # 名前付きVolume
```

**疑問: volumeを使う場合は永続的だからといって、docker-compose.ymlのトップレベルにvolume定義がないと実行時エラーになる？**

**回答: Yes.**
名前付きボリューム（例: `db-data`）をサービス内で使用する場合、ファイル末尾（トップレベル）の `volumes:` ブロックでの宣言が必須です。
この定義が欠けていると、Dockerは「未定義のボリュームを使おうとしている」と判断し、`Service "db" uses an undefined volume "db-data"` というエラーを出して起動を停止します。

</details>

### Q16. `COPY` と `ADD` の違いとして正しいのは？

- A) `COPY` はファイルのみ、`ADD` はディレクトリのみをコピーする
- B) `ADD` は圧縮ファイル（tar）の自動展開やURLからのダウンロード機能を持つ。通常は動作が明確な `COPY` を使うべき
- C) `COPY` は本番環境専用、`ADD` は開発環境専用
- D) 両者に違いはなく、どちらを使っても同じ

<details>
<summary>答えを見る</summary>

**正解: B**

**解説:**

| 機能 | COPY | ADD |
|------|------|-----|
| ローカルファイルコピー | ✅ | ✅ |
| ディレクトリコピー | ✅ | ✅ |
| tar自動展開 | ❌ | ✅ |
| URLダウンロード | ❌ | ✅（非推奨） |

**ベストプラクティス:**  
通常は **`COPY` を使う**。動作が予測しやすく、意図が明確だから。
`ADD` は「tar展開が必要な特殊なケース」だけに限定する。

```dockerfile
# 良い例
COPY package.json ./

# 避けるべき例（意図が不明確）
ADD app.tar.gz ./   # ← 勝手に解凍されて中身が配置される！
COPY app.tar.gz ./  # ← 圧縮ファイルのまま配置される
```

**💡 用語解説: 「tar展開」とは？**
`.tar.gz` などの圧縮ファイルを「解凍（展開）」することです。
- **`ADD` の場合:** `data.tar.gz` を指定すると、Dockerが気を利かせて勝手に解凍し、中身のファイル群を配置してしまいます。「そのまま圧縮ファイルとして置きたい」ときに困ります。
- **`COPY` の場合:** 勝手なことはせず、圧縮ファイルのままコピーします。挙動が素直なので、基本はこちらを使います。
```

</details>

### Q17. Dockerfile で `COPY . .` する前に `COPY package.json .` を書いて `RUN npm install` するテクニックの目的は？

```dockerfile
# 悪い例
COPY . .
RUN npm install

# 良い例
COPY package*.json ./
RUN npm install   # ← ライブラリをダウンロード
COPY . .          # ← ソースコードをコピー
```

- A) package.json に構文エラーがあった場合に早期発見するため
- B) 並列ビルドを有効にしてnpmの処理速度を上げるため
- C) ライブラリのインストール結果をキャッシュさせ、ソースコード変更時にはキャッシュを再利用してビルド時間を短縮するため
- D) Node.jsのセキュリティ要件を満たすための必須構文

<details>
<summary>答えを見る</summary>

**正解: C**

**解説:**
Dockerはレイヤーごとにキャッシュを持ちます。そして「**COPYしたファイルの中身が変わると、それ以降のすべてのレイヤーのキャッシュが無効化**」されます。

```
【悪い例の問題点】
COPY . .        ← ソースコード（頻繁に変わる）も含む
RUN npm install ← ソースが変わるたびに npm install やり直し！（数分かかる）

【良い例のメリット】
COPY package*.json ./  ← 依存関係ファイルのみ（めったに変わらない）
RUN npm install        ← package.json変更時のみ実行
COPY . .               ← ソースコードは後！
```

**結果:** ソースコードを修正しても、npm installはスキップされる！

</details>

### Q18. `RUN` と `CMD` の違いは？

- A) RUNはイメージビルド時に実行され、CMDはコンテナ起動時に実行される
- B) RUNはLinuxでのみ、CMDはWindowsでのみ動作する
- C) RUNは1回のみ、CMDは複数回実行される
- D) 両者に違いはなく、どちらも同じ動作をする

<details>
<summary>答えを見る</summary>

**正解: A**

**解説:**

| 命令 | 実行タイミング | 用途 |
|------|--------------|------|
| `RUN` | イメージ**ビルド時** | パッケージインストール、ビルドなど |
| `CMD` | コンテナ**起動時** | アプリケーションの起動コマンド |

</details>

      retries: 5

      db:
        condition: service_healthy  # ← ヘルスチェック通過まで待つ！
```

### Q21. コンテナ間で通信する際、接続先ホスト名として `localhost` を使うと失敗する理由は？

### Q25. Dockerにおける「Dockerデーモン」の役割は？

- A) コンテナ内部で実行されるメインプロセス（PID 1）のこと
- B) Docker Hubと通信するためだけの専用プロキシ
- C) コンテナイメージをビルドする時だけ起動する一時的なツール
- D) ホストマシン上でバックグラウンド実行され、クライアント（docker コマンド）からの命令を受けてイメージ管理やコンテナ実行を行う常駐プロセス

<details>
<summary>答えを見る</summary>

**正解: D**

**解説:**
Dockerは「**クライアント・サーバー型**」のアーキテクチャです。

```
【Dockerのアーキテクチャ】
┌─────────────────────────────────────────┐
│              ホストOS                    │
│  ┌─────────┐     ┌──────────────────┐  │
│  │ docker  │ →→→ │  Docker Daemon   │  │
│  │ コマンド │     │   (dockerd)      │  │
│  │(クライアント)   │ ↓                │  │
│  └─────────┘     │ イメージ管理      │  │
│                  │ コンテナ起動/停止 │  │
│                  │ ネットワーク管理  │  │
│                  └──────────────────┘  │
│                        ↓               │
│              ┌──────────────────┐      │
│              │ コンテナA コンテナB │      │
│              └──────────────────┘      │
└─────────────────────────────────────────┘
```

**覚えておくポイント:**
- **Docker Client(`docker`コマンド)**: 私たちがターミナルで入力する「窓口」です。
- **Docker Daemon(`dockerd`)**: 裏側で常駐し、イメージの管理やコンテナの起動を行う「職人さん」です。
- **Docker Engine**: Daemon、Client、APIなどを全てセットにした、Dockerを動かすためのシステムの総称です。
- デーモンが動いていないと、Client（コマンド）を打っても「そんな職人はいません（Cannot connect to the Docker daemon）」と拒否されます。

</details>

      POSTGRES_USER: user

      POSTGRES_DB: mydb

volumes:
  db-data:

【Step 3: 起動】

### Q27. 【新規プロジェクト】上の構成で開発中にソースコードを変更した時、コンテナを再起動せずに反映させるにはどうすればよい？

- A) 毎回 `docker compose build && docker compose up` を実行する
- B) Docker Desktop の「Auto Reload」機能を有効にする
- C) 常にソースコードをイメージにハードコードして再ビルドする
- D) ホストのソースコードディレクトリをボリュームとしてマウントし、nodemonなどのホットリロードツールを使う

<details>
<summary>答えを見る</summary>

**正解: D**

**解説:**
開発時はソースコードを頻繁に変更するため、毎回イメージを再ビルドしていては効率が悪いです。

```yaml
services:
  app:
    build: .
    volumes:
      - .:/app                   # ← ホストのカレントディレクトリをコンテナの/appにマウント
      - /app/node_modules        # ← node_modulesはコンテナ内のものを使用（上書きしない）
    command: npm run dev         # ← nodemon等でホットリロード
```

**この設定で:**
1. ホストでファイル保存
2. コンテナ内の `/app` に即時反映
3. nodemonが変更を検知して再起動
4. ブラウザを更新して確認

**注意:** 本番環境では、ソースコードはイメージに `COPY` でベイクインすべき。ボリュームマウントは開発用。

</details>

- A) `docker compose up` を実行するだけで、必要なイメージのダウンロードからコンテナ起動まで全て行われる

<details>
<summary>答えを見る</summary>

### Q29. 【既存プロジェクトへの追加】Redisを新しく追加したい場合の手順は？

- A) ホストOSにRedisをインストールし、IPアドレスをアプリに設定する
- B) docker-compose.ymlにRedisサービスを追加し、アプリの環境変数で接続設定し、`docker compose up` を再実行
- C) 新しくredis用のdocker-compose.ymlファイルを作成し、別のターミナルでdocker compose upを実行
- D) Docker Hubで「redis-with-node」のような統合イメージを探してそれを使う

<details>
<summary>答えを見る</summary>

**正解: B**

**解説:**
Docker Composeの真価が発揮される場面です！

```yaml
# docker-compose.yml（変更前）
services:
  app:
    build: .
    environment:
      DATABASE_URL: postgres://...
  db:
    image: postgres:15

# docker-compose.yml（変更後）
services:
  app:
    build: .
    environment:
      DATABASE_URL: postgres://...
      REDIS_URL: redis://redis:6379    # ← 追加
    depends_on:
      - db
      - redis                           # ← 追加
  db:
    image: postgres:15
  redis:                                 # ← 追加
    image: redis:7-alpine
```

```bash
$ docker compose up
# → 自動的にRedisがダウンロードされ、起動し、appから接続可能に！
```

**チームメンバーへの共有:**
- 変更をgit pushするだけ
- 他メンバーは `git pull && docker compose up` で同じ環境に

</details>

### Q30. コンテナ技術の「イミュータブル（不変）インフラストラクチャ」の考え方で正しいものは？

- A) 一度起動したサーバーは設定変更ができないため、ハッカーによる改ざんを完全に防げる
- B) データの書き込みができないため、データベースのバックアップが不要になる
- C) 問題が発生したら「修正して直す」のではなく「新しいイメージに置き換える」ことで、環境の再現性と一貫性を保つ
- D) サーバーの管理コストがゼロになる

<details>
<summary>答えを見る</summary>

**正解: C**

**解説:**
従来のサーバー運用（ミュータブル）と、コンテナ時代の運用（イミュータブル）の違い：

```
【従来：ミュータブル（変更可能）】
サーバー起動 → sshでログイン → 設定変更 → ライブラリ追加 → ...
→ 変更履歴が追えない、環境差異が発生、再現が困難

【コンテナ：イミュータブル（不変）】
Dockerfile修正 → 新イメージビルド → 古いコンテナ削除 → 新コンテナ起動
→ 変更はすべてDockerfileに記録、いつでも同じ環境を再現可能
```

**ペットと牛の例え:**
- **ペット（従来）**: 名前をつけて、大事に育て、具合が悪くなったら治療する
- **牛（コンテナ）**: 個体識別せず、問題が起きたら新しいのと交換する

**❌ 不正解の解説:**
- **A**: 実行中のコンテナも書き換えは可能です。ただし「捨てて作り直せる」のが利点。
- **D**: 適切な設計と運用は依然として必要です。

</details>

## 📖 参考：重要用語ミニ辞典

チェックリストに出てきた分かりにくい用語のまとめです。

| 用語 | 意味をエンジニア的に解説 |
| :--- | :--- |
| **ハイパーバイザ** | 物理的なPCの中に、別の仮想的なPC（VM）をまるごと作るためのソフト。VirtualBoxなどが有名。 |
| **カーネル (Kernel)** | OSの心臓。アプリが「ファイルを開いて！」と命令すると、実際にハードウェアを動かす役割。Dockerはホストのこれを使い回すから速い。 |
| **Docker Engine** | Dockerの本体。デーモン、コマンドライン、APIなどが全部入ったパッケージ。 |
| **Docker Daemon (dockerd)** | Docker Engineの一部。裏方でずっと起きていて、コンテナの面倒を見る常駐プログラム。 |
| **Docker Client** | 私たちが叩く `docker` コマンドのこと。命令を Daemon に投げるだけの役割。 |
| **ホストOS** | Dockerをインストールしている大元のOS（あなたのMacやWindows、またはLinuxサーバー）。 |
| **ゲストOS** | VM（仮想マシン）の中で動いているOS。DockerにはゲストOSは存在しない。 |
